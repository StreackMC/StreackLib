# 2026-11-09

## 核实「SdbActionContext 不支持参数化写入」的说法（结论：已过期，非现行缺陷）

用户带来一句外部断言：「UPDATE 的 SET 直接抛 UnsupportedOperationException、参数化分支只生成
`UPDATE tbl SET ?`、MERGE 同样残缺、`act(String)` 走 Statement 无参数位」。逐条复核并写成探针实测。

**探针做法**（无真实连接）：`StreackLib.ENV.conf` 是 public static 字段，直接注入
`new SConfig("", TYPES.JSON, null)` 并 `putString("databases.probe.mode", "sqlite")`，即可
`new SdbDatabase("probe")` → `db.act(ACTION_TYPE.X)`，只调用 `toString()` / `toPrepared()`。
classpath = `target/classes:$（mvn -o dependency:build-classpath 的输出）`；`getMode()` 是包级私有，
探针放默认包时不能调用，靠传入 mode 字符串绕开。

**实测结果**：
- UPDATE：`UPDATE `users` SET `name` = ?, `age` = ? WHERE `id` = ?`，params `[abc, 20, 7]`
- MERGE（sqlite）：`INSERT OR REPLACE INTO `users` (`name`, `age`) VALUES (?, ?)`
- MERGE（mysql）：`INSERT INTO ... VALUES (?, ?) ON DUPLICATE KEY UPDATE `name`=VALUES(`name`), ...`
- COMMIT：这才是唯一仍抛 UnsupportedOperationException 的类型

**溯源**：commit `5da9b6e` 曾用 UnsupportedOperationException 临时封堵 UPDATE/MERGE（因为当时会
拼出非法 SQL），紧接着 `d66b4ca` 就实现了完整逻辑（读 param 作 SET 列、按 mode 选方言、MERGE 跳过
WHERE、新增 `getMode()`）。断言停留在 `5da9b6e` 那一版的状态。

**仅存的事实点**：`act(String)` → `SdbAction.apply(String)` 确实用 `Statement`，没有参数位——但这是
文档明确声明的有意设计（原始 SQL 调用方全责），参数化入口是 `apply(SdbActionContext)`。
真正残留的相关限制见 MEMORY.md 第 ②④ 条（`.next()` 多语句不能过 apply()、构造器 package-private）。

顺手修正了 MEMORY.md 里 2026-08-12 遗留的 ① 号「已知缺陷」——它已经不再是缺陷。
