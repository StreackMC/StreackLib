### 关键设计决定（用户已确认）
1. 命名：抽象基类 `SUDSAbsLink`，具体类 `SUDSServerLink` / `SUDSClientLink`
2. 协议通过构造器传 `SUDSProtocol` 枚举
3. `onMessage` 为 JS 风格回调注册式（重载 `Consumer` 与 `MessageListener`，返回 ID 可注销）
4. LF 分帧符由**链路**在 `send` 时追加，不放进 `SUDSPayload` 的字节里——
   否则「收到再转发」的载荷不会被对端识别为完整报文

### 踩到的坑
- 客户端必须用 `SocketChannel.open(UNIX)`；`ServerSocketChannel` **没有** `connect()`
- `MAP_TYPE.equals(type)` 判定后 `json(data, MAP_TYPE).getValue()` 会因泛型被推断成 `Object` 而编译失败，
  必须先落到 `SUDSPayload<R> parsed = ...` 局部变量
- 服务端与客户端为同一条连接**各自**生成 `SUDSPeer`，两侧 ID 不同、不可跨进程比较（已写入 JavaDoc 与文档）
- `SUDSClientLink.isRunning()` 需实现为 `isConnected()` 才与基类 JavaDoc 语义一致（自检抓到）
- token 含路径分隔符会导致服务端建目录/客户端失败行为不一致 → 已在 `resolveSocketPath` 直接拒绝

## 追加调研：SUDSPayload 为何不复用 SConfig 解析 JSON（2026-10-07）

写了三个探针（`/tmp/suds-harness/JsonReuseProbe.java`、`SConfigWriteProbe.java`、`SConfigFlushProbe.java`）
实测对比，结论是「不复用」成立，并顺带发现 **SConfig 三个真实缺陷**（见 MEMORY.md 已知缺陷）：

- JSON 含 `null` 值 → `new SConfig(text, JSON, null)` 直接抛
  `RuntimeException: 无法加载配置文件：null`（`ConcurrentHashMap` 不接受 null value）
- `SConfig.save()` 对 **JSON / TOML** 写出 **0 字节文件**（`getWriter()` 返回的 `OutputStreamWriter`
  从不 flush，Gson 的 `toJson(obj, Writer)` 也不 flush）→ 数据丢失级
- JSON/JSONC 解析失败**静默返回空 Map**（`BackendJSONc` 里 `catch (Exception ignore) {}`；
  `BackendJSON` 对非对象/数组根也返回空 Map），报文场景下无法区分「空报文」与「坏报文」

另：`SConfig` 的 JSON 后端内部同样是 `JsonParser` + `new Gson().fromJson(el, TypeToken<Map<String,Object>>)`，
与 SUDSPayload 现实现是同一套调用，复用省下的代码极少，但实测解析吞吐慢 **约 2.5–3 倍**
（20000 次：自研 ~19–26ms vs SConfig ~54–73ms，主因是每次 `new Gson()` + 锁 + 中间流）。
