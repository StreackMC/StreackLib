# 2026-10-14 工作日志

## 修复：SConfig 嵌套路径「写读不对称」（库调用者反馈，已完成）

调用者反馈「depth ≥3 的写全部是写得进、读不出」，实测证据是 YAML 里出现键名被拼成
`<uuid>.preset-code` 的怪键。已复现、定位、修复并双向验证。

### 根因
`getIndexOfNormalDot(key)` 返回的是**第一个**未转义点，但两处调用方把它当「最后一个点」用：

```java
int lastDot = getIndexOfNormalDot(key);              // ← 实际是第一个点
String lastKey = key.substring(lastDot + 1);         // ← 于是把「第一个点之后的所有内容」当键名
targetMap.put(lastKey, value);
```

而 `ensureNestedMap` 又确实会按 `splitWithNormalDot` 逐层创建中间层，于是：
`putString("a.b.c","v")` → `{a={b={"b.c"=v}}}`（多一层 + 叶子键名带父级前缀），
`getString("a.b.c")` → 按 `a→b→c` 下探 → 找不到 → null。

受影响面（走同一套错误推断的位置）：
- `putNested()`（所有 `putXxx`）与 `remove()`
- **深度 1/2 恰好正确**（第一个点就是最后一个点），所以只在 depth ≥3 暴露
- 有趣的副作用：`put` 与 `remove` 用的是同一套错推断，所以「刚 put 再 remove」看起来正常，
  **真正的破绽是「删一条从磁盘加载进来的、正确嵌套的数据」——静默无操作**

### 修复（SConfig.java）
1. **删掉 `getIndexOfNormalDot` 这个陷阱本身**，改为 `hasNestedPath(key)`（只回答有没有嵌套）。
   返回值语义无法被误读，从根上消灭「把第一个点当最后一个点」这类错误。
2. **`splitWithNormalDot` 定为路径分段的唯一权威**（JavaDoc 写明，并列出 `a.b.c` / `a\.b.c` 示例）。
3. `getNested()` 重写为按分段迭代下探（取代原先「substring(0,dot) + 递归 drillDown」），
   顺带删掉不再需要的 `drillDown()`。
4. `putNested()` / `remove()` 的叶子键名改为 `parts.get(parts.size() - 1)`。
5. 新增 `ensureNestedMap(Map, List<String>)` 重载，避免同一条路径被重复切分。
6. `putNestedRaw()`（Properties 加载）与 `isReachable()` 一并对齐到 `hasNestedPath`。

### 顺手修掉的第二个同类不对称（转义点）
原实现里读侧**不做转义还原**、写侧只对中间段还原：
- `putString("a\\.b.c", ...)` → 结构 `{a.b={c=v}}`（正确），但读不回来（读侧去找字面 `a\.b`）；
- `putString("x.y\\.z", ...)` → 叶子键留成 `y\.z`（应为 `y.z`），读写「互相将错就错」才看起来正常。
现在三处共用同一套分段，读写的转义语义完全一致，并有断言锁定
（`a.b` 与 `a\.b` 是两个不同的键、`a\.b.c` 可读写可删）。

### 顺带修掉的第三个同类问题（INI 静默损坏）
INI 后端对节内的嵌套值直接 `String.valueOf(map)`，把 `{leaf=v}` 当字符串写进文件（写得进、读不出）。
与上一轮「INI 顶层标量静默丢成 0 字节」属同一政策，改为显式抛 `IllegalArgumentException`
并列出非法项；节内 List 同样拒绝（INI 值只能是字符串）。

### 需要调用者注意的两件事
1. **已被本 bug 写坏的历史文件不会自动修复**：那些 `uuid.preset-code` 形式的字面键在修复后
   依然读不出来（结构本来就是错的）。需要重新写一遍，或手工把键名改回来。
2. `remove()` **不会连带清理空的父级 Map**（删完会留下 `{a={b={}}}`），已写进 JavaDoc；
   属既有行为，未改。

### 经验
- 「写得进、读不出」这类反馈，第一件事是**看写侧怎么推断叶子键名**，并与读侧的
  下探逻辑逐行对照——两侧路径解析一旦不共用同一个分段函数，深度一上来必然分叉。
- **深度 1/2 正确、深度 ≥3 崩**的缺陷很容易在手工试验里漏掉（人习惯用 `a.b` 这种两级路径），
  断言必须按深度循环覆盖到 5~6 级。
- 「功能正常但保存后重启丢失」的现象要优先怀疑**写侧把结构写歪了**，
  而不是怀疑 flush / 权限 / 时序——本例中「保存当时能 work」正是因为读写错得「互相对齐」。
