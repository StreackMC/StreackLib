### 关键设计决定（用户已确认）
1. 命名：抽象基类 `SUDSAbsLink`，具体类 `SUDSServerLink` / `SUDSClientLink`
2. 协议通过构造器传 `SUDSProtocol` 枚举

   否则「收到再转发」的载荷不会被对端识别为完整报文

- 客户端必须用 `SocketChannel.open(UNIX)`；`ServerSocketChannel` **没有** `connect()`
- `MAP_TYPE.equals(type)` 判定后 `json(data, MAP_TYPE).getValue()` 会因泛型被推断成 `Object` 而编译失败，

- token 含路径分隔符会导致服务端建目录/客户端失败行为不一致 → 已在 `resolveSocketPath` 直接拒绝

## 追加调研：SUDSPayload 为何不复用 SConfig 解析 JSON（2026-10-07）

写了三个探针（`/tmp/suds-harness/JsonReuseProbe.java`、`SConfigWriteProbe.java`、`SConfigFlushProbe.java`）
实测对比，结论是「不复用」成立，并顺带发现 **SConfig 三个真实缺陷**（见 MEMORY.md 已知缺陷）：

- JSON/YAML **顶层** 含 `null` 值 → `new SConfig(text, JSON|YAML, null)` 直接抛
  `RuntimeException: 无法加载配置文件：null`（`ConcurrentHashMap` 不接受 null value）；
  嵌套层的 null 不受影响（项目自己的 `config.yml` 就是这样才活下来的）
- `SConfig.save()` 对 **JSON / TOML** 写出 **0 字节文件**（`getWriter()` 返回的 `OutputStreamWriter`
  从不 flush，Gson 的 `toJson(obj, Writer)` 也不 flush）→ 数据丢失级
- JSON/JSONC 解析失败**静默返回空 Map**（`BackendJSONc` 里 `catch (Exception ignore) {}`；
  `BackendJSON` 对非对象/数组根也返回空 Map），报文场景下无法区分「空报文」与「坏报文」

另：`SConfig` 的 JSON 后端内部同样是 `JsonParser` + `new Gson().fromJson(el, TypeToken<Map<String,Object>>)`，
与 SUDSPayload 现实现是同一套调用，复用省下的代码极少，但实测解析吞吐慢 **约 2.5–3 倍**
（20000 次：自研 ~19–26ms vs SConfig ~54–73ms，主因是每次 `new Gson()` + 锁 + 中间流）。

## 追加讨论：SUDSPayload 向 JS `Response` 风味靠拢（2026-10-07，待用户拍板）

用户设想 `SUDSPayload` = JS 的 `Response`。已给出评估与方案，**尚未实施**：

- 纠正类比：SUDS 是**双向对等**的，应类比 WebSocket 的 `MessageEvent.data`，而不是 fetch 的
  `Response`（后者有 status/ok/url/请求-响应模型，SUDS 没有）。
- 最能落地且有价值的一条：**把「类型在构造时定死」改成「消费时才决定」**——
  `SUDSPayload<T>` 要求 `T` 在解析前就确定，这与 JS「`await res.json()` 拿到动态对象」的精神冲突；
  实操代价已出现：链路侧 `onMessage` 只给 `SUDSPayload<?>`，取 RAW 载荷必须写 `(byte[]) payload.getValue()`。
- 拟改为对称的 JS 风味命名（0.6.2 未发布，可无痛改名）：
  构造 `json(Object)` / `text(String)` / `bytes(byte[])` / `of(...)`；
  消费 `json()` → `Map`（可变、缓存）、`config()` → `SConfig`（路径取值）、`text()`、`bytes()`、`as(Class|Type)`。
  `json(byte[])` 解析方向收敛为链路内部使用，顺带消掉 `json(byte[])` 与 `json(Object)` 的歧义。
- `Map` 与 `SConfig` **都给**，分工：Map≈JS 普通对象（直接 get/put/转 POJO），
  SConfig≈取值工具（`getString("a.b.c")`）。这样 SConfig 只出现在消费侧、不参与解析，
  闭环了上一问的结论；且它处于 MEMORY 模式，`save()` 必抛异常，天然踩不到写盘 0 字节那个 bug。
- `headers` 不建议假装：不做线上头，元数据挂 `SUDSPeer`（协议、字节数、来源、时间）；
  若确需头，走用户层约定（JSON 里放约定键），不进传输层——否则只有内置协议能用，等于给两种协议造两套语义。
- 不建议照抄：`bodyUsed` 一次性消费（Java 无需求，是 JS 里最易踩的坑之一；我们可重复读，不需要 `clone()`）；
  惰性解析（保持「收到即校验 + 缓存结果」，坏报文要早发现）。
- **待用户决策**：`SUDSPayload<T>` 的 `<T>` 留还是去。建议保留但降级为「发送侧类型自述」，
  接收侧一律走视图方法。


## 实施：SUDSPayload 去泛型 + JS 风味重构（2026-10-07，已完成）

用户拍板：**去掉 `<T>`**（降低调用者理解成本），按上一节的方案动工，已提交。

### 最终 API（`SUDSPayload`，非泛型）
- 构造（发送）：`json(Object)`、`text(String)`、`bytes(byte[])`、`bytes(byte[],off,len)`、
  `of(byte[] data, boolean raw)`（最底层，其余都是它的语法糖，不校验）
- 解析（接收/离线）：`parse(byte[] line)` —— **严格**：JSON 语法 + 要求对象根；
  链路接收路径用它（`SUDSPeer.consumeFramed`），校验一次并缓存解析结果
- 消费视图：`json()`→`Map`（缓存同一实例、保持键序、可变）、`config()`→`SConfig`、
  `text()`、`bytes()`（拷贝）、`as(Class)`/`as(Type)`
- RAW 载荷上 `json()/config()/as()` 抛 `IllegalStateException`（而非 JSON 语法错），语义清晰
- 包内 `wrapRaw(byte[])` 接管数组所有权，RAW 读循环因此省一次拷贝

### 两处实现要点（都实测过）
- `config()` 走 `new SConfig(Map, JSON, null)` **复用已解析结果**，不重复解析；但 SConfig 的
  `this.cache = rD` 是**直接引用不拷贝**，所以必须传 `new LinkedHashMap<>(json())` 顶层拷贝，
  否则 `config().put(...)` 会污染载荷的 `json()` 缓存（已加自检用例锁定）
- 该 Map 构造器**绕过** `ConcurrentHashMap`，因此容忍顶层 null（与 String/File 构造器相反）；
  但 SConfig 的 `getRawData()` 用 `Map.copyOf` 仍会 NPE —— 已在文档中标注，含顶层空值的载荷改用 `json()`

### 同步改动
- `SUDSPeer`/`SUDSAbsLink`/`SUDSServerLink`/`SUDSClientLink`：去掉 `SUDSPayload<?>` 通配符，更新 JavaDoc 示例
